# P1 协议 v1.0 预注册前审计

**审计日期**：2026-11-02
**审计对象**：`protocol-P1-v1.0.md`
**结论**：设计可冻结，但**第 3 项（统计口径）和第 5 项（异常规则）存在未定义项，必须补充后才能开跑**。第 1、2、4 项有小缺口。

---

## 一、提示词一致性

### 已核对

| 对比 | 差异 | 判定 |
|---|---|---|
| D1 vs B | 仅多「生成后自己验收并打分，比较哪张最好」 | ✅ 符合预期 |
| D1 vs A 第 1 轮 | 逐字相同 | ✅ |
| D1 vs C 第 1 轮 | 逐字相同 | ✅ |
| T-D1 vs T-B | 仅多「写完后自己验收并打分，比较哪份最好」 | ✅ |

### 发现的问题

**P1-1：D3 比其他组少了「每张一个不同场景」**

D1/D2/A/C 都有「每张一个不同场景」，D3（1 张）没有。这是有意的（1 张不需要「每张」），但构成额外差异。

**处理建议**：保留，但在协议里明确注明「D3 因单张不适用『每张』句式，属有意差异，不是遗漏」。

**P1-2：B 组的评价句包含「比较哪张最好」**

B 组消息是「生成后自己验收并打分，比较哪张最好」。这比 T-B 的「比较哪份最好」多了「哪张」——但这是模态差异导致的自然措辞，可接受。

**处理建议**：保留，注明措辞随产物单位（张/份）变化。

## 二、模型与接口

### 已定义

- 模型：`gemini-3.1-flash-image`
- `responseModalities: ["TEXT","IMAGE"]`
- 不传 temperature

### 发现的问题

**P1-3：未定义 `max_output_tokens`**

A/C 两组第二轮需要一致的最大输出预算，协议只说「保持一致」，没给具体值。

**处理建议**：图像组全部设为 `max_output_tokens: 8192`（或 API 默认），A/C 第二轮相同。写入协议。

**P1-4：未定义 `candidateCount`**

Gemini `generateContent` 默认 `candidateCount=1`。一次请求返回多张图是通过单个 candidate 的多个 `inlineData` part 实现，不是多个 candidate。

**处理建议**：显式设 `candidateCount: 1`，避免默认值变化。写入协议。

**P1-5：未定义图片尺寸**

模型可能返回不同分辨率（之前观察到 1408×768、1024×1024 等）。

**处理建议**：不强制指定尺寸（指定可能改变模型行为），但**每次记录实际尺寸**，分析时作为协变量。

**P1-6：未定义 API 版本与端点**

**处理建议**：固定 `v1beta`，端点 `https://generativelanguage.googleapis.com/v1beta/models/gemini-3.1-flash-image:generateContent`。写入协议。

**P1-7：未定义 safety filter 设置**

Gemini 默认启用安全过滤，可能拒绝「卧室女孩」类提示。

**处理建议**：使用默认设置（不调整），但记录 `promptFeedback.blockReason`。如果出现拒绝，按异常规则处理。

## 三、统计口径（最需要补充）

### 已定义

- 有效图片 = 独立产物，拼图算 0
- 完整交付 = 达到要求数量

### 发现的问题

**P1-8：未定义「重复图片」**

如果模型返回两张几乎相同的图（同一画面微调），算 1 张还是 2 张？

**处理建议**：算 2 张（原始计数），但**额外标记 `duplicate`**，分析时同时报告「原始数」和「去重后数」。不直接剔除，避免主观。

**P1-9：未定义「主题偏离图片」**

之前观察到防呆条件下模型把主题换成「人像摄影光线控制」，图是真的，但内容不是要求的。

**处理建议**：算**有效产物**（真实交付了图片），但标记 `topic_drift: true`。单独报告「主题保持率」。不并入欠交付。

**P1-10：未定义「失败调用」的计数**

API 报错、超时、safety 拒绝，这些运行在统计里算什么？

**处理建议**：
- 记为 `error` 运行，**不计入有效产出**
- **保留在分母**（即 n 包含失败运行），单独报告失败率
- 不剔除，不补跑（除非按异常规则重试成功）

**P1-11：未定义「图片损坏/无法读取」**

**处理建议**：记为 `corrupt`，不计入有效产出，保留记录。

**P1-12：未定义「部分成功」的判定**

例如一次调用返回 5 张图 + 1 张损坏。算 5 张有效还是 6 张？

**处理建议**：算 5 张有效，记录 raw=6, valid=5。

## 四、随机化与记录

### 已定义

- 每组每次独立新会话
- 正式实验按时间区块随机交错

### 发现的问题

**P1-13：未定义 run_id 格式**

**处理建议**：`P1-{group}-{index:03d}`，如 `P1-D1-001`、`P1-A-017`。A/C 两轮用 `turn` 字段区分。

**P1-14：未定义随机化方法与种子**

**处理建议**：用固定种子（`seed=20261102`）生成执行顺序，记录种子和顺序表，任何人可复现。

**P1-15：未定义证据保存结构**

**处理建议**：
```
p1-data/
├── runs/
│   └── P1-D1-001/
│       ├── request.json      # 完整请求
│       ├── response.json     # 完整响应
│       ├── images/           # 返回图片
│       └── meta.json         # 计数、时间戳、finishReason
├── order.json                # 随机顺序表
└── seed.txt                  # 随机种子
```

**P1-16：未定义会话 ID 记录**

A/C 两轮同会话，需要记录 conversation_id 或 turn 关联。

**处理建议**：`meta.json` 里记 `session_id`，A/C 两轮用同一 session_id。

## 五、停止与异常规则（最需要补充）

### 已定义

- 失败运行记录，不得删除

### 发现的问题

**P1-17：未定义超时时间**

**处理建议**：单次请求超时 90 秒。超时记为 `error: timeout`，**不自动重试**（避免引入重试偏倚）。

**P1-18：未定义服务端错误重试策略**

**处理建议**：
- HTTP 5xx 或 429：重试 2 次，间隔 5 秒
- 重试成功：正常记录，`retried: 2`
- 重试失败：记 `error`，保留
- **4xx（除 429）不重试**（请求本身有问题）

**P1-19：未定义 safety filter 拒绝处理**

**处理建议**：记 `error: blocked`，`blockReason` 写入 meta。**不重试、不改提示词**。

**P1-20：未定义预算耗尽处理**

**处理建议**：设硬预算上限（如 $20）。达到上限即停止，记录已完成 n，**不凑数、不删已完成的运行**。

**P1-21：未定义连续失败处理**

**处理建议**：连续 3 次失败，暂停 10 分钟检查（可能是服务端问题），再继续。记录暂停原因。

**P1-22：未定义模型拒答（非 safety，是模型自己说不做）**

**处理建议**：记 `refused`，保留完整响应，不计入有效产出。
